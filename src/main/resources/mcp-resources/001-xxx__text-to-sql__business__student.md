# 学员（student）业务说明

> 示例 Resource：用于演示 Bear MCP 如何把业务口径文档当作可检索资源暴露给模型。
> 表名、字段与口径均为教学用简化版，与本仓库代码无耦合。

## 一、这张表是什么

`student` 记录一名学员的主体信息与当前归属。一名学员在同一时刻只属于一个校区、一个班型；
学员与课程的关系不在这张表里，而是拆到 `student_product`（购买关系）与 `sys_class_schedule`（排课关系）。

## 二、核心字段口径

| 字段 | 含义 | 口径说明 |
| --- | --- | --- |
| `id` | 学员主键 | 自增，不对外暴露，对外用 `student_no` |
| `student_no` | 学员编号 | 业务唯一键，创建后不可变 |
| `name` | 姓名 | 可能重名，禁止作为唯一条件 |
| `mobile` | 手机号 | 明文存储，查询结果输出前必须脱敏为 `138****0000` |
| `campus_id` | 归属校区 | 与 `sys_campus.id` 关联，跨校区数据需权限校验 |
| `status` | 状态 | 1=在读，2=休学，3=退费结案，0=潜在客户 |
| `create_time` | 建档时间 | 首次录入系统的时间，不等于报名时间 |

## 三、常见统计口径

1. **在读人数**：`status = 1` 且存在未过期的 `student_product` 记录。
2. **新增学员**：按 `create_time` 落在统计周期内计数，退费不冲减。
3. **退费人数**：按 `order_refund` 中审核通过的时间计数，与 `student.status` 解耦。
4. **活跃学员**：统计周期内存在 `student_learning_calendar` 打卡记录。

## 四、易错点

- 用 `name` 做关联会导致重名合并，必须用 `student_no` 或 `id`。
- `status` 与「是否有有效课程」是两件事：休学学员可能仍有未消课课时。
- 退费后 `student` 行不会删除，历史查询不要按 `status <> 3` 过滤掉退费记录。
- 手机号脱敏必须在最终输出层完成，不要在 SQL 里做字符串截断，否则影响对账。
