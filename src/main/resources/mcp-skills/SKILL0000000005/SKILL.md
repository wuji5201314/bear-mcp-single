# 线上日志排查 Skill（示例）

本 Skill 演示 Bear MCP 中「可发布到数据库、由模型按需加载」的技能包结构。
它只是一份排查方法论模板，不包含任何真实系统、账号或内网信息。

## 适用场景

- 接口返回 5xx，需要定位是参数、下游依赖还是自身逻辑问题
- 用户反馈某笔业务办理失败，但前台只显示「操作失败」
- 同一类异常在短时间内重复出现，需要判断是否为同一根因
- 已知 traceId 或业务单号，需要还原一次请求的完整链路

不适用于：纯前端样式问题、性能压测数据解读、与业务数据无关的基础设施故障。

## 排查步骤

1. **固定输入**：确认时间范围（精确到分钟与时区）、环境、traceId 或业务单号、影响面（单用户 / 单租户 / 全量）。
2. **拉日志**：按 traceId 聚合，先看首条 ERROR，再看它之前 3 秒内的 WARN，异常堆栈取最内层 Caused by。
3. **分层定位**：入口参数 → 鉴权与权限 → 业务校验 → 数据库/缓存/第三方调用 → 序列化与返回包装。每层只需回答「这一层是否正常」。
4. **验证假设**：每个假设都要给出可执行的验证动作（查一条 SQL、重放一次请求、看一项监控指标），不要凭堆栈猜结论。
5. **收敛结论**：区分「已证实」与「待验证」，写明触发条件、影响范围和临时处置手段。

## 输出格式

```
现象：<一句话>
根因：<已证实/待验证>
证据：<日志片段或数据，脱敏后>
影响：<范围 + 时间>
处置：<临时方案 / 长期修复>
遗留：<需要继续跟进的事项>
```

## 约束

- 输出中不得出现密钥、Token、身份证号、手机号、内网地址等敏感内容，必要时用 `xxx` 占位。
- 不确定就写不确定，禁止编造日志行、表名或接口返回。
- 涉及写操作（改数据、重跑任务）只给建议，不直接执行。
